# Phase 3 UI and API actions

Phase 3 implements correction-plan sections 8–11. Phase 1/2 security and worker separation remain in place. Google Workspace production login is deferred; public development sessions remain forbidden. SQLite stays live.

## Workflow actions

The editor displays the canonical status, server revision, unsaved state and actual server-provided save timestamp (or explicitly says the timestamp is unavailable for legacy revisions). Save draft, Validate, Submit for approval, Approve, Publish and Activate are independent buttons. Each explains its permission and state blocker. A shared in-flight lock disables conflicting actions. Publish requires a clean approved revision; it does not save, validate, approve or activate. Activation requires its own confirmation and preserves lifecycle operation/idempotency behavior.

Save draft uses `save_workflow_version` against the last known base version. The server records the save time and clears old approval/submission authority. Validation and approval retain existing server/Registry checks. `POST /workflows/{id}/submit-for-approval` is an additive transport action using the canonical response envelope and exact revision/idempotency binding. It requires validation permission, a current validated revision and a ready Registry review. It records `metadata.approval_submission` (submitter, time, revision); it does not introduce a new v1 status or confer approval. Submitted revisions appear in the Approvals page. Approval remains an explicit server-authorized `approve_workflow` operation. Shared contract schemas are unchanged.

Approval permissions remain server-owned. Runtime decisions require server `allowed_decisions` as well as `workflow.approve` in the UI. This does not implement Google Workspace identities or a new production separation-of-duties policy.

Dirty server drafts and their edited agents persist in the browser under the existing storage key. Background initialization and editor fetches do not replace dirty drafts. If edits arrive while save/validation is in flight, the confirmed server baseline advances while newer local edits remain dirty. Reload server revision offers an explicit discard confirmation; conflicts preserve the local edit and explain how to copy desired changes, reload and reapply. No automatic merge or conflict overwrite is attempted. Links, shared router navigation, browser Back and tab unload protect unsaved drafts. Browser-local draft storage is not server persistence and can be lost if browser data is cleared.

Duplication creates a local draft with isolated agent IDs; editing the copy cannot alter the source agents. It clears approval/submission metadata and trigger binding IDs. Save draft is required to persist it. Saved revision viewing fetches the exact historical revision into a read-only dialog and never replaces the current draft. Rename and graph edits remain local until Save draft. Workflow/local deletion and release disabling confirm their destructive effect, preserve history according to server policy, and refresh only after confirmation.

## Run inputs

Run published requires `workflow.execute`, available runtime and an actual published canonical revision. The dialog loads that published version, not the editable draft. Required strings, finite numbers, safe integers, explicit booleans and JSON arrays/objects are validated before submission. Optional empty inputs are omitted. JSON `null` is not an object. Cancellation makes no execution request. Entered values remain visible after server errors.

Event-only workflows explain that activation and a new source event are required and expose no manual submission. Manual submissions use an immediate lock plus the existing durable payload-bound client idempotency key, preserving retry identity if the form/client is reopened after an uncertain outcome. An uncertain result does not permit silently changing payload and replaying it. Confirmed pre-execution validation/authorization errors permit correction. Successful submission displays the server run ID/status and links `/app/runs?run={id}`, which loads that exact run and timeline. The Phase 2 API still queues real execution for the separate worker.

## Settings and integrations

Settings uses the validated canonical client, loads the confirmed server value before enabling edits, checks HTTP/envelope/data contracts, requires server administrative authority, prevents repeated submissions and preserves entered values on failure. Success/time are displayed only after matching server confirmation. Failed initial loading cannot overwrite an unknown setting. Reload is explicit and confirms discarding unsaved setting input. Backend notification preferences accept text up to 2000 characters, reject secret material, and retain the previous value on failure. Settings values remain preferences; this change does not create a new notification delivery service.

Integration cards distinguish Not configured, Configured (not verified), Verified and Connection failed. Check configuration consults visible enabled Registry records and required credential configuration. It never infers successful connectivity from an environment variable. Unsupported live probes explicitly state that connectivity/resource access has not been verified. Unknown providers or browser-supplied credentials/destinations are rejected.

A server-installed SMTP probe supports administrator-only Verify connection using a fixed trusted Gmail host, TLS, authentication and NOOP. It never sends MAIL/RCPT/DATA, email or modifies an external resource. It has bounded network timeouts. Automated tests replace the SMTP transport and verify the command sequence; deployment smoke does not call live provider verification. Other providers stay configuration-only until a safe resource-specific probe is installed. Google account/Sheet access is not claimed verified by a configured Registry record.

Knowledge loading and reply actions now distinguish failures from empty data, validate canonical safe envelopes and prevent overlapping submission/refresh. Local governance/agent controls explicitly identify draft-only effects and do not claim to stop live execution or enforce server policy. Unsupported source ingestion/connector installation is labeled unavailable instead of showing simulated success.

## Action inventory and verification

Run `node frontend/scripts/audit-actions.mjs` to regenerate every inspected source control/handler; use `--check` for drift. Then run `python scripts/generate_action_audit.py` to refresh the human-readable matrix with its reviewed owner policies. `openspec/changes/phase3-correct-ui-actions/action-audit-matrix.md` maps all controls to owner behavior, endpoints, required permissions, success/errors and actual test coverage. Loops are recorded by source expression; delegated UI primitives remain caller-owned. The inventory is not a claim of a dedicated browser test for every unused design-system primitive.

Regression checks cover explicit lifecycle transitions, draft/agent isolation, conflict and in-flight edit preservation, navigation warnings, typed run validation/cancellation/deduplication, saved historical viewing, review permissions, confirmed settings, unsafe/failed responses, provider-check semantics and SMTP no-send behavior. Real isolated browser API tests run lifecycle, typed deterministic execution and settings save/reload on desktop/mobile. Offline fixtures cover permission/provider failures. Production build verification occurs outside the running frontend directory. See the Phase 3 verification report for exact passing/failing/unexecuted results and live rollout evidence.
