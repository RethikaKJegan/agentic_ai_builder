# Phase 5 draft synchronization and safe feedback

The backend canonical revision is the persisted baseline. The UI retains a separate working graph/agents. Mapping clones mutable condition/approval/UI data, preserves supported layouts and unknown canonical metadata, and tracks all workflow-owned agents including delegated specialist templates without graph nodes. New editable revisions clear tool grants, tool configuration references and prior approval/submission/validation metadata. Save still uses the exact base revision and authoritative shared-schema/Registry validation; editing never changes an existing release.

Server reads reconcile atomically at response time. Clean newer documents may replace the baseline. Older versions and older lifecycle states cannot downgrade confirmed state. Dirty working drafts remain intact; different server documents become explicit conflict evidence. Unchanged reads do not persist or broadcast state, avoiding storage notification loops. Initial bulk loading uses one reconciliation update instead of one full store/persistence update for every workflow. This reduces repeated client work; it does not implement pagination or claim the existing large overview is fast.

The editor checks its exact workflow on focus, on relevant browser storage events and with a bounded 30-second background read. It coalesces an overlapping focus/storage check, retains edits on failures and distinguishes unsaved local 404 from a failed saved-workflow read. Local drafts can discover an accepted first save after a lost response without sending the mutation again. Actual save confirms the server baseline only after the canonical response passes validation; edits entered in flight remain dirty.

Conflict resolution is explicit: inspect loaded/remote JSON, export a recoverable working-draft bundle (including invalid unfinished edits), retain this tab's draft, confirm discard/reload, or request a non-overlapping three-way rebase. Rebase compares fields and canonical keyed entities against the loaded baseline, refuses overlapping edits and deletion/change conflicts, and does not save, approve, publish or activate anything. Subsequent Save uses the newly selected server base and still needs fresh Registry review. Reload refuses to discard edits entered after its confirmation while its read was in flight. A server race after rebase still returns a normal revision conflict; no forced overwrite or last-write-wins save is introduced.

The existing shared draft key/version remains `mesh-local-drafts-v1` / 1. Each tab additionally saves its recovery bundle in `sessionStorage` under `mesh-tab-drafts-v1`; that tab's working copy takes precedence on reload while dirty. This prevents another tab's shared-storage writes from replacing its open/reloaded working draft. A storage write failure stays visible with an export option. Browser storage is not a durable server backup: clearing browser/session storage or closing a tab may lose its recovery copy. Cross-tab notices do not confer server authority or import another tab's local draft automatically.

The validated client and shared ApiFeedback expose safe codes, request/correlation references, exact field/related errors, session/permission/conflict guidance, and unknown mutation outcomes. Unexpected local exception messages are generic; intentionally authored local InputError validation remains actionable. Credential/stack-like server text is not displayed. Run inputs show exact field errors with aria-invalid/described-by. The monitoring screen uses the validated client instead of rendering raw fetch failures and avoids overlapping interval requests. Current nullable runtime fields are validated explicitly.

Only one additional GET retry is allowed for allowlisted retryable transient 502/503/504 responses. Invalid data, 401/403 and arbitrary business failures do not enter that retry path. Existing explicit local session rejection recovery is still bounded and preserves the same body/key. Uncertain mutations are never automatically replayed. Existing canonical payload-bound retry keys remain durable; procurement supplier review and fulfilment activation now use that same behavior rather than generating a new key on every explicit retry. An HTTP success with an invalid mutation response remains unconfirmed. Confirmed recovery clears stale action/overview errors without erasing unrelated failures.

No backend code, API route, shared schema, credentials, connector write or database migration is introduced by Phase 5. Safe simulation stays explicitly unavailable; production Google Workspace login remains deferred. Public development sessions remain blocked. Large unbounded overview/run/monitoring collections remain later pagination/scaling work. Verification and exact review patches are in `openspec/changes/phase5-state-synchronization/`.
