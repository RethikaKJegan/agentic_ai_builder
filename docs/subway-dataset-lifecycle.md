# Automatic Subway dataset selection and lifecycle

Ordinary new Subway business requests automatically use the active, validated demonstration dataset. For example, `Investigate purchase-order discrepancies and prepare an evidence-backed report.` requires no dataset name, version or phrase. The same resolution applies to summaries, deterministic assessments and newly reviewed recurring workflows. The dedicated deployment enables this behavior with `BUILDER_SUBWAY_DEMO_DEFAULT_ENABLED=1` alongside the existing demo opt-in.

`workflow_api/subway_dataset_lifecycle.py` is the common tenant-aware resolver. Overview resolves before model routing and saves the source contract in its durable intent. Action preparation consumes that exact contract, including during bounded planner corrections. The workflow stores `validated_context.source_resolution`, its immutable `demo_context`, dataset hash, numeric revision, ontology and rule versions, query namespace and registry generation. Models receive the resolved metadata; they cannot choose a foreign source or switch versions. Existing query, assessment and document connectors resolve from saved workflow authority. Adaptive replanning copies that authority; retries, worker restart, receipt validation and recurring consent keep the same version. There is no automatic migration of approved workflows or schedules, and no follow-latest execution permission is inferred.

Explicit `Use historical Subway records to ...` selects the genuine restored historical sources. Explicit `Use Subway demonstration dataset v1.` or `Use Subway dataset <dataset-id>.` selects an available validated retained version. A request for real current operations is rejected with `SUBWAY_CURRENT_SOURCE_UNVERIFIED`; restored snapshots cannot prove current coverage. If the automatic policy is enabled but no eligible active version exists, the system returns `SUBWAY_DATASET_UNAVAILABLE`. It does not fabricate data or silently use historical sources. Deployments without the automatic-default flag retain their prior historical behavior.

The existing `subway_demo_datasets` and `subway_demo_records` tables keep immutable manifests and records. The active-version registry is one tenant-owned `workspace_settings` document, with schema/validation/provenance/dependency metadata. `subway_demo_lifecycle_audit` records bootstrap, registration, activation, retirement, resolution and archive/restore events. Startup validates the existing 192 records and their ontology without regenerating or rewriting them. The original v1 query namespace and legacy demo descriptors remain compatible with approved workflows. Older historical workflows lacking a demo pin continue using historical records.

The dedicated Subway backend exposes these existing-application management routes under `/business-ontology/v1/subway/datasets` (the existing UI proxy prefixes `/api/backend`):

| Method/path | Behavior |
| --- | --- |
| GET base path | Inventory active/retained versions and protected dependencies |
| POST base path | Register `{document, ontology_version, activate}`; `activate` defaults to true |
| POST `/{dataset_id}/activate` | Validate and atomically activate a retained compatible version |
| POST `/{dataset_id}/retire` | Retire it; clears the default pointer if it was active |
| POST `/{dataset_id}/cleanup` | Archive and remove only eligible obsolete demo operational rows |
| POST `/{dataset_id}/restore` | Verify and restore the retained archive as retired |

Reads require the authenticated Subway subject and workspace read scope. Management additionally requires existing workflow approval authority and workspace write scope. These routes are installed only by the dedicated Subway configured launcher. Nothing is installed into Simpson.

Registration requires a unique dataset identity and positive numeric revision, exact tenant/provenance/manifest hashes, compatible nested collection schemas and native identity types, valid cross-record relationships, invoice/header/line/payment consistency, finite financial balances, an existing compatible Subway ontology and the supported typed rule contract. A new source must retain the currently supported collections and illustrative policy; changing policy, schema or engine semantics requires a reviewed runtime change. Numeric revisions, not dataset-name sorting, determine upgrade order. Registration plus validation, prior retirement and active-pointer update occur in one transaction; a failed check rolls back the entire operation. New workflows follow the new active version; saved ones remain pinned. Compatible versions may reuse the existing modeled ontology and rule definitions rather than rebuilding them.

Cleanup inventories saved revisions, runs, compositions, receipts, automation records, Knowledge Map references, settings, shared ontology references and source-resolution audit. Active versions, the base v1 schema dependency, referenced data, historical sources, credentials, all audit, shared ontology and backups are protected. Unreferenced retired non-base versions can have their two operational data-table entries removed only after a hash-verified recovery archive is saved in the same store. Archives and audit are retained. Restore verifies the archive and compatibility before reinserting records. No production cleanup is forced when nothing qualifies; the current v1 is active and referenced and is retained.

Reports retain modeled provenance and record/knowledge hashes. Existing Knowledge Map evidence descriptions include the actual selected dataset ID and revision alongside the applied rules and fields. There is no new frontend or execution engine. Gmail, Calendar, sender/recipient permissions and external-action approvals are unchanged; verification sends no real communications.
