# Phase 6 — monitoring, approval authority and readiness

Run and event history use bounded reads. `GET /runs` accepts `limit` (1–500, default 100), `cursor` (exclusive durable insertion position), `workflow_id`, canonical `status`, `from_date`/`to_date` (ISO UTC dates/timestamps, inclusive), and `pending_only=true|false`. Filtering happens before LIMIT; total counts the matching workspace population. New inserts do not shift older keyset pages. A cursor is a position, not an authorization token. Run timestamps are additive public metadata; inputs and credentials remain private.

`GET /runs/{id}/events` accepts `limit` and `after_sequence` (exclusive persisted sequence). It returns the existing collection envelope, has_more and next_cursor. On reconnection consumers resume after their last fully confirmed sequence and validate event ID, sequence and exact run/revision. The current UI loads one page at a time, deduplicates, retries interrupted reads with 3–30 second backoff and retains confirmed data. Selected active runs refresh every 3 seconds; completed, failed, blocked, rejected and cancelled runs stop after draining their remaining event pages. Explicit Refresh/Load remains available. Concurrent consumers share in-flight selected-run/event reads only; no response cache grants authority.

Run lists refresh serially every 15 seconds, with workflow/status/date filters and Older/Newest navigation. The editor requests workflow-scoped history and exposes older runs. Monitoring refreshes serially every 15 seconds. Workflow overview now uses one serialized 15-second polling loop, without a competing EventSource; refresh calls share an in-flight read. The legacy overview SSE endpoint remains a finite compatibility batch and identifies its bounded-polling strategy. It is not a persistent subscription. The global workflow collection and initial overview remain unbounded; this phase paginates run/event/readiness history, not all workflow discovery.

Monitoring aggregates run counters in SQL instead of materializing every run and workflow document. Latest traces and audit records are bounded. Trigger and enforced-revision evidence default to 50 items per page (maximum 500), with independent `source_cursor` and `policy_cursor` positions. It displays trigger provider/type/source/schedule/timezone, preparation success, active/disabled/failed release state, baseline, last successful poll and stable health error. Preparation readiness is separate from connectivity and actual poll success. A disabled release cannot receive active automation. Trigger documents, credential references, signing secrets and raw provider errors are not returned.

Activation retains configuration validation and current exact Registry checks before and after provider preparation. Configured live polling additionally requires an installed connector, current polling-tool grant and an explicit source resource. Unsupported incoming adapters and missing HMAC signing secrets fail closed with durable failure/cleanup evidence. Existing signature verification, deduplication, leases and effect retry boundaries are preserved. Configuration checks do not send email or modify remote resources.

Runtime approval decisions now require `workflow.approve`, a role in the exact saved gate's `approver_roles`, and authenticated workspace membership. Previously workspace members could decide a gate without its role: this is intentionally rejected. Read responses project required roles and eligible allowed decisions without modifying stored evidence. Browser role flags confer no server permissions. Existing configured gates whose role is not assigned to any real identity remain blocked until an authorized policy revision is reviewed; this phase does not rewrite live gates.

Governance separates browser-only drafts from read-only backend-enforced revision evidence. The displayed policy scope and effective active release/revision are explicit; a newer browser draft cannot alter an active release. Browser draft edit UI requires a server-authenticated administrator. Production-managed policy editing remains unavailable until backend persistence and validation are implemented; no toggle claims to change production policy.

Google Workspace production login remains deferred by user. Public development session issuance stays denied. Full manual testing continues through the explicitly local authenticated application. Phase 7 full release qualification remains pending.
